# Code audit findings — tofix4

Each item is a self-contained prompt for an LLM. Verify against current code before fixing.

## High — logic / UX

1. **FIXED — Launching any SAF picker triggers the background relock — the vault closes behind the picker and the operation finishes silently (or is cancelled).**
   In `MainActivity` the `ON_STOP` observer closes the vault (`showVault.value = false`) unless `externalViewActive` was set, and `onExternalView()` is called only from the file-view action in `FileListScreen`. But the import-files picker (`OpenMultipleDocuments`), the import-folder picker and the export-destination picker (`OpenDocumentTree`) all launch a full-screen system activity, which stops `MainActivity` and takes the non-exempted `ON_STOP` path: the vault relocks while the picker is open. On return the `ActivityResultRegistry` delivers the result before recomposition, so the callback coroutine starts, but the next frame disposes `FileListScreen` and cancels its `rememberCoroutineScope` — the blocking `withContext(Dispatchers.IO)` body typically runs to completion, then the coroutine dies at the suspension point, so `refreshItems()` and the result Toast never run. Net effect: the user picks files/destination, lands on the calculator, must re-enter the PIN, and gets no feedback whether the import/export happened (it usually did, silently; in unlucky timing it may be partially cancelled). Fix: exempt picker launches the same way as the external viewer — call the existing exemption callback (rename `onExternalView` to something like `onExternalActivity`) right before each `launcher.launch(...)` in `FileListScreen`, so the one-shot `ON_STOP` exemption plus the existing 60-second `ON_START` relock apply. Verify on a device/emulator that import, folder import and both export flows keep the vault open and show their toasts.

## Medium — data integrity / performance

2. **FIXED — Imported encrypted blobs are never fsynced — power loss right after an import can leave the index pointing at a truncated `.enc` file.**
   `VaultRepository.saveMetadata()` carefully fsyncs the index temp file before the atomic rename (tofix3 item 5), but `importFile()` writes `${id}.enc` via a plain `encFile.outputStream()` with no `fd.sync()` before `saveMetadata()` persists the entry referencing it. After power loss / battery pull, ext4 can leave the blob empty or truncated while the fsynced index survives with the entry: GCM authentication then fails on every open ("Failed to open file") and the content is unrecoverable — the user may have already deleted the original, trusting the import. Fix: in `importFile`, write via `FileOutputStream` and call `out.fd.sync()` after `CryptoManager.encrypt` completes, before saving metadata. Same pattern is already used in `saveMetadata`, so mirror it (a temp-file + rename is optional here since a partial blob without a metadata entry is already cleaned by the orphan sweep).

3. **FIXED — The Move dialog queries the repository on the main thread during composition — and can block behind a long-running import holding the instance lock.**
   In `FileListScreen`, the move dialog does `val allFolders = remember { listOf(rootLabel) + repository.getAllFolderPaths() }` — a repository call executed synchronously in the composition. `getAllFolderPaths()` → `loadMetadata()` is `@Synchronized` on the repository instance, and `importFile()` is also `@Synchronized` and holds the same lock for the entire encryption of a file (potentially a large video on `Dispatchers.IO`). Opening the move dialog while an import is running blocks the UI thread until the import finishes — jank or ANR; even without contention, the first load does disk + AES + JSON on the main thread. Fix: load the folder list asynchronously — e.g. `var allFolders by remember { mutableStateOf<List<String>?>(null) }` filled from a `LaunchedEffect` with `withContext(Dispatchers.IO)`, showing the dialog content when ready (the rest of the screen already follows this pattern via `refreshItems`).

## Low — robustness / cleanup

4. **FIXED — `uniqueDocumentFile` gives extension-less files a trailing dot on name collision (`"foo (1)."`).**
   In `VaultRepository.uniqueDocumentFile()`, `ext` is computed as `name.substringAfterLast('.', "").let { if (it == name) "" else ".$it" }`. `substringAfterLast('.', "")` returns `""` (not `name`) when there is no dot, so the `it == name` guard is dead code and `ext` becomes `"."` — exporting a duplicate of an extension-less file creates `"foo (1)."` instead of `"foo (1)"`. Fix: change the guard to `if (it.isEmpty()) "" else ".$it"`. Optionally also handle dot-leading names (`.bashrc` currently yields base name `""` → `" (1).bashrc"`), e.g. treat a name whose only dot is at index 0 as having no extension.

5. **FIXED — Folder import reports only the success count — files that failed to import inside the tree are silently ignored.**
   `FileListScreen`'s `folderPickerLauncher` callback always shows `R.string.imported_files` with `imported.size`; `importDocumentRecursive` drops `importFile` nulls without counting them, so a tree where some files failed (unreadable URI, encryption error) looks fully imported. The plain multi-file import already distinguishes (`imported_failed`). Fix: make `importFolder`/`importDocumentRecursive` return attempted and succeeded counts (or collect failures), and reuse the existing `imported_failed` string in the toast when `failed > 0`.

6. **FIXED — Corrupt-index backups accumulate unboundedly, and a failing backup copy crashes the caller.**
   In `VaultRepository.mutableMetadata()`, every process that fails to load the index creates a new `metadata.enc.corrupt-<timestamp>` copy — with a persistently corrupt index each app launch that opens the vault adds another full-size copy forever. Worse, `metadataFile.copyTo(backup)` runs inside the `catch` block: if it throws (disk full, IO error), the exception escapes `mutableMetadata()` with `metadataCache` still null, crashing the calling coroutine (vault open). Fix: wrap the `copyTo` in its own try/catch (log on failure, still fall through to the empty list), and avoid duplicates — e.g. skip the backup if one with identical content/size already exists, or keep only the most recent N backups.

7. **FIXED — PIN fail counting uses `apply()` — force-killing the app right after a wrong attempt can lose the increment.**
   `PinManager.registerFailedAttempt()` persists `fail_count`/`cooldown_until` with `prefs.edit().apply()`, which writes to disk asynchronously. An attacker can try 2 PINs, swipe the app away before the async write lands, and repeat — the 3-attempts/30s cooldown never engages. The write is tiny and happens at most once per attempt, so synchronous cost is negligible. Fix: use `commit()` (on a background-safe path — the call already happens from a coroutine; move it inside `Dispatchers.IO` if needed) for `registerFailedAttempt` and the cooldown write; `clearFailures` may keep `apply()`.

8. **FIXED — Deleting a selection with several folders rewrites the encrypted index once per folder.**
   The delete dialog in `FileListScreen` calls `repository.deleteFiles(files)` (one batched save) but then loops `for (f in folders) repository.deleteFolder(f.path)` — each `deleteFolder` call re-encrypts, fsyncs and renames the whole metadata file, so deleting N sibling folders costs N full index writes plus one for the files. Fix: add a batched `deleteFolders(paths: List<String>)` (or extend `deleteFiles` into a combined `deleteItems`) in `VaultRepository` that removes all matching entries and their `.enc` blobs, then saves metadata once; keep single-folder `deleteFolder` delegating to it.

## Tests

9. **`VaultRepositoryTest.moveFilesBetweenFolders` and `renameFile` mutate the defensive copy returned by `loadMetadata()` — both tests are broken.**
   Since `VaultRepository.loadMetadata()` was changed to return `mutableMetadata().toList()` (a defensive copy, tofix1 item 4), the test pattern `val meta = repo.loadMetadata() as MutableList; meta.add(file)` no longer registers the entry in the repository: the added `VaultFileMetadata` exists only in the discarded copy, so `repo.moveFiles(...)` / `repo.renameFile(...)` find no matching id and silently no-op, and the subsequent assertions fail. In `renameFile` the snapshot has exactly one element, so Kotlin's `toList()` returns a `SingletonList` and `meta.add(file)` throws `UnsupportedOperationException` before the assertions even run. Fix: give tests a legitimate way to insert a file entry — e.g. a `@VisibleForTesting internal fun addEntryForTest(meta: VaultFileMetadata)` in `VaultRepository` (add + saveMetadata under the lock), or import a real temp file through `importFile` with a `file://` URI — and update both tests to use it; never cast `loadMetadata()`'s result to `MutableList`.

10. **Instrumentation tests wipe the real app's vault and PIN when run on a device with live data.**
    `VaultRepositoryTest.setUp()` executes `File(context.filesDir, "vault").deleteRecursively()` and `PinManagerTest.setUp()` clears and deletes the real `vault_pin_prefs` files — both against `targetContext`, i.e. the actual installed app's private storage. Running `connectedAndroidTest` on a personal device that holds a real vault permanently destroys the encrypted index and all vault blobs (the PIN loss is recoverable, the index is not). Fix: make the vault location injectable (e.g. `VaultRepository(context, baseDir: File = context.filesDir)`) and point tests at a dedicated test subdirectory, and give `PinManager` an injectable prefs name; at minimum, add a guard in `setUp()` that aborts (`Assume`/`fail`) when an existing non-empty `vault/files` directory or a set PIN is detected, so tests refuse to run over live data.
